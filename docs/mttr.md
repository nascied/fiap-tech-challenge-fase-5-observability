# MTTR — como a stack de observabilidade ajuda a reduzir

> Requisito do Hackathon Fase 5 (seção *SRE*): *"evidencie no relatório como a stack de observabilidade e as automações de resposta a incidentes ajudam a reduzir ativamente o MTTR (Mean Time To Recovery)"*.

**MTTR (Mean Time To Recovery)** = tempo médio entre a detecção de um incidente e o serviço voltar a operar normalmente. Não é uma métrica única — é a soma de várias fases (detecção → diagnóstico → decisão → correção → validação), e cada peça deste projeto ataca uma fase diferente.

## Onde cada componente entra

| Fase do incidente | Sem a stack (cenário hipotético) | Com a stack deste projeto |
|---|---|---|
| **Detecção** | Alguém percebe manualmente ou um usuário reclama | Painel "SLO — Disponibilidade"/"SLO — Latência" (`solidary-tech-sre-donation`) mostra o Error Budget caindo em tempo real **+** 9 `PrometheusRule` de burn rate multi-window (`alerting/prometheusrule-slo-burn.yaml`) roteadas por `severity`/Tier pro Slack via Alertmanager — não depende mais só de alguém *olhar* o dashboard (ver ressalva de "nunca sincronizado" abaixo) |
| **Diagnóstico — "o que quebrou?"** | `kubectl logs` manual, pod por pod, sem correlação | Painel de logs (Loki) por serviço, filtrado por `namespace`/`app`, direto no mesmo dashboard onde já se viu o sintoma — sem trocar de ferramenta |
| **Diagnóstico — "onde exatamente, e por quê?"** | Adivinhação, reprodução manual do bug | **Distributed tracing** (Datadog APM → Traces): o trace de uma doação (`donations` → `db.insert_donation` → `sqs.publish_donation_event`, ver [README do repo `services`](https://github.com/nascied/fiap-tech-challenge-fase-5-services#-observabilidade--tracing-distribuído)) mostra exatamente qual span falhou ou ficou lento — banco, fila, ou a própria aplicação — sem precisar instrumentar nada na hora do incidente |
| **Diagnóstico — "é saturação de recurso?"** | Suspeita sem dado | Painel "Saturação — CPU/Memória (% do limit)" no dashboard SRE já correlaciona no tempo com o pico de latência/erro |
| **Decisão — "o que fazer agora?"** | Decisão ad-hoc, sob pressão, no meio do incidente | [Runbooks do DRP](../../fiap-tech-challenge-fase-5-infra/docs/drp/) já documentam o passo a passo pra RDS, DynamoDB e cluster — a decisão já foi tomada com calma, antes do incidente acontecer |
| **Correção — drift de configuração** | Alguém "consertando na mão" direto no cluster, gerando mais um desvio do Git | ArgoCD `selfHeal: true` (todas as Applications, ver `fiap-tech-challenge-fase-5-gitops`) reverte automaticamente qualquer alteração manual pro estado do Git — remove uma classe inteira de "correção manual que quebra de novo depois" |
| **Correção — perda de dado** | Recriar backup/restore do zero, sob pressão | Runbooks prontos com os comandos exatos (`rds-restore.md`, `dynamodb-restore.md`, `eks-velero-restore.md`) — RTO documentado por componente, não descoberto na hora. Pro cenário de cluster EKS perdido, os comandos de infraestrutura (bootstrap → init → plan → apply → kubeconfig) já são scripts versionados em `fiap-tech-challenge-fase-5-infra/scripts/` (ver `README.md` lá), não `terraform` digitado na hora sob pressão |
| **Validação pós-correção** | "Parece que voltou", sem confirmação | Os mesmos dashboards usados na detecção confirmam objetivamente: SLI voltou a subir, Error Budget parou de cair, taxa de erro 5xx voltou a zero |

## O que isso NÃO inclui ainda (honestidade sobre o estado atual)

- **Os alertas de burn rate existem e foram validados de verdade** (`promtool check rules` + `amtool check-config`), **mas nunca foram sincronizados contra um cluster real** — a `Application` `alert-rules` no ArgoCD nunca rodou de fato, e o Secret `alertmanager-slack-webhook` que o Alertmanager espera ainda não foi criado. Até isso acontecer, a detecção na prática ainda depende de alguém *olhar* o dashboard. A IA do APM (Watchdog Datadog/Applied Intelligence) continua bloqueada à parte — depende de uma conta Datadog real, não só de sincronizar o cluster (ver `docs/itsm-aiops.md`).
- **Nenhum MTTR real foi medido ainda** — este documento é a justificativa *arquitetural* de por que a stack deveria reduzir o MTTR, não um número medido. Pra virar dado real (e não só teoria) pro relatório, falta rodar um **drill de verdade**: provocar uma falha controlada (ex.: derrubar o `donation-pg-db`) e cronometrar detecção → diagnóstico → correção → validação usando exatamente o fluxo acima. O [`fiap-tech-challenge-fase-5-infra/docs/drp/drills/TEMPLATE.md`](../../fiap-tech-challenge-fase-5-infra/docs/drp/drills/TEMPLATE.md) já tem o formato certo pra registrar isso — é o mesmo template, só que agora com a stack de observabilidade também disponível durante o drill, não só o runbook.
